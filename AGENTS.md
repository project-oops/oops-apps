# AGENTS.md — oops-apps

Rules for any agent working on a title, a dependency or a shim here. The collection's shared
rules are in [`../AGENTS.md`](../AGENTS.md) and [`../docs/CONVENTIONS.md`](../docs/CONVENTIONS.md);
this file is what is specific to porting.

---

## The four rules

**1. Go through the SDK wherever possible.** A title reaches the console through `oops-sdk`. If a
port needs a facility — storage, input, logging, a dialog, a clock — the SDK is where it comes
from and, if it is missing, where it goes.

**2. Check the SDK before reimplementing anything.** Read
[`../oops-sdk/docs/API_INDEX.md`](../oops-sdk/docs/API_INDEX.md) first. It lists every public
entry point by header, and is regenerated by `../oops-sdk/tools/api-index.sh`. Grep finds a name
you already guessed; the index lets you recognise a concept without knowing its name.

**3. A shim is minimal, and belongs to one title.** `shim/` holds what is true of *that title
only*. Anything a second port would want is not a shim — it is an SDK entry point, or it lives in
[`common/`](common/).

**4. A patch is minimal, and belongs to one title.** `patches/` changes upstream only where
upstream is wrong for this target. A patch that adapts the platform rather than the program is
the platform's job, not the patch's — a patch is carried, rebased and re-read forever.

---

## Where a fix goes, in one line

The four rules above say what each place is for. This says how to choose, and it is the operator's
own wording:

> **Anything reusable goes in the SDK, anything non-reusable into the shim, anything game-specific
> into a patch.**

Ask it of the *fix*, not of the bug. The question is never "which title found this" - it is "who
else would want it":

| the fix | where | why |
|---|---|---|
| a home directory that has to exist before a program can write | SDK / `common/` | every port asks for one |
| naming the file and errno of a failed `open` | SDK | every port's loader fails silently |
| an upstream tree fetched byte-for-byte as published | `common/` | every fetched title |
| `-DOS_LINUX=1`, an entry point, five forwarding headers | that title's `shim/` | true of that program only |
| a hard-coded `main`, a path only this program builds | that title's `patches/` | upstream's own source, and only where it is wrong for this target |

**The test that catches the mistake:** if the same fix would be needed by the next port, and it is
sitting in a title, it is in the wrong place - however local the bug looked when it was found. Three
of the five rows above were discovered by one title on one afternoon and none of them belong to it.

## Why these are rules and not preferences

Each was written after being broken, and each cost a hardware run or a session.

| what happened | which rule |
|---|---|
| `OOPS_GL_LOG_*` and `OOPS_INPUT_LOG_*` invented beside the existing `oops_log_level_t` | 2 |
| A savedata path hand-rolled beside `oops_savedata_mount` | 2 |
| A writable directory searched for, when `/app0` already was one | 2 |
| `getenv`/`setenv` written into a title, then found to belong in the SDK's libc | 1 |
| A `/app0/gl-debug` marker in Neverball's shim, to reach a log level every port needs | 3 |

The last one is the shape to watch for, because it looks correct while you write it: the code
worked, it was small, and it was in one title's shim. The next port would have needed its own
copy under its own name. It became `oops_log_channel_level` in the SDK — `/app0/oops-log`, one
`channel=level` per line — and titles now need no code for it at all.

**The test, before writing anything into a title:** ask what the *next* port would have to copy.
If the answer is "this code", it is in the wrong place.

## Telemetry is the thing that makes the next port cheap

Every port hits the same walls in the same order: a slow frame, a wrong pixel, a missing libc
name. The first port pays to build the instrument that finds each one. **If that instrument lives
in a title, the second port pays again.**

So diagnostics — counters, log channels, a way to turn verbosity up without a rebuild — go in
`oops-sdk` or `common/`. Before adding one, check what is already measured: oops-gl already
counts triangles, draw calls, GPU wait, shader patching and command-buffer time per flip, and
prints them when `/app0/oops-log` carries `gl=debug`.

## Build and verify

The collection is pinned to clang 21 and the pin is enforced. Do not use the host's compiler:

`<OOPS>` is wherever the collection is checked out — a real path does not belong in a committed
file, and the identity guard refuses one.

```bash
MSYS_NO_PATHCONV=1 docker run --rm -v "<OOPS>:/w" \
    -w /w/oops-apps/src/<category>/<app> silkeh/clang:21 make all
```

`MSYS_NO_PATHCONV=1` is for Git Bash, which otherwise rewrites `/w` into a Windows path before
Docker sees it.

A build failing on paths under `/mnt/c/...` is stale dependency output from a WSL build in
another session: `rm -rf build` in that app and rebuild.

`./bin/oops-apps list | build | check | dist` reach every app the way CI does.
